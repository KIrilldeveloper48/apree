# Правила разработки

Этот репозиторий содержит локально запускаемый задачник: веб-клиент на
React/Next.js и Material UI, API на NestJS и PostgreSQL. Все постоянные данные
хранятся в PostgreSQL; браузер не является источником истины.

## Стек и границы

- Frontend: TypeScript, Next.js (App Router), React и Material UI.
- Backend: TypeScript, NestJS, REST API и PostgreSQL.
- Доступ к данным и миграции: Prisma. Схема Prisma и все миграции хранятся в
  репозитории.
- Runtime-валидация: Zod на границах frontend (URL, формы, localStorage и
  ответы API) и `class-validator`/`class-transformer` в DTO NestJS. Типы
  TypeScript не заменяют runtime-валидацию.
- Инфраструктура: Docker Compose поднимает PostgreSQL. Frontend и API
  запускаются локально командами package manager; Docker для них не обязателен.
  Это сохраняет быстрый цикл разработки и делает конфигурацию БД повторяемой.
- API документируется через OpenAPI/Swagger и имеет префикс `/api`.

Не добавляйте авторизацию, совместное редактирование, вложения, облачное
развёртывание или другую функциональность за пределами согласованного ТЗ без
отдельного решения.

## Организация кода

- Используется monorepo с рабочими пространствами: `apps/web` и `apps/api`.
  Общие контракты разрешены только в `packages/contracts`; не импортируйте
  исходный код одного приложения из другого.
- Связанные handler, types, helpers, schemas и tests с общим назначением
  размещайте в отдельной подпапке функционального модуля.
- Каждый собственный type alias или интерфейс хранится в отдельном файле
  `*.types.ts`, даже если тип один. Type aliases начинаются с `T`, интерфейсы —
  с `I`.
- Исключения: inline-типы сторонних библиотек и обязательные ambient module
  augmentation, форму которых задаёт библиотека.
- Вспомогательные функции размещайте в `*.helpers.ts`. В HTTP handlers
  (контроллерах) остаются только разбор запроса, вызов бизнес-логики и
  формирование ответа.
- Код объясняет себя небольшими функциями, ясными именами и узкой зоной
  ответственности. Комментарии объясняют причины и ограничения, а не
  пересказывают код.
- Новая абстракция появляется после второго обоснованного повторения, а не
  заранее. Между коротким и более очевидным кодом выбирайте очевидный, если он
  сохраняет производительность и архитектурные границы.

## TypeScript и модели

- Не используйте неявный `any`, небезопасные type assertions (`as`) и
  невалидированные приведения данных извне.
- Для неизменяемых моделей, DTO и входных параметров чистых функций применяйте
  `readonly`-поля и `readonly T[]`, если мутация не является частью контракта.
- Публичные модели и все границы приложения — URL, HTTP, формы, localStorage —
  проверяются во время выполнения. Ошибки валидации имеют понятную структуру.
- Сначала проектируйте и тестируйте чистые функции и модели, затем API-адаптеры,
  после этого UI. Бизнес-правила не дублируются между UI, API-клиентом и
  MSW-моками.
- У задачи есть `id`, `title`, `description`, `priority`, `status`,
  `createdAt` и `updatedAt`. Значения `priority` и `status` — закрытые
  перечисления, одинаково валидируемые на API-границе и в базе данных.

## Backend и база данных

- API реализует создание, список, получение одной задачи, обновление и
  удаление задачи, а также смену статуса для перемещения между колонками
  «Новая», «В работе», «Готово».
- Бизнес-правила находятся в сервисах и чистых helpers, а не в контроллерах.
- Любое изменение структуры данных сопровождается миграцией Prisma. Миграции не
  редактируются задним числом после применения: создаётся новая миграция.
- Обрабатывайте ошибки в едином HTTP-формате; не возвращайте внутренние детали
  БД клиенту.
- Конфигурация считывается из переменных окружения, проверяется при старте и
  описывается в `.env.example`. Секреты и реальные `.env` не коммитятся.

## Frontend, доступность и состояния

- Компоненты отвечают только за представление и взаимодействие пользователя.
  Загрузка данных, преобразования и бизнес-правила выносите в hooks, model или
  lib.
- Предпочитайте композицию небольших компонентов: один компонент — одна
  заметная часть интерфейса или сценарий. Props описывайте явными типами.
- Производное состояние вычисляйте из данных вместо дублирования в `useState`.
- Интерфейс должен быть удобен на широком экране и телефоне: на desktop — три
  колонки, на узком экране — доступный горизонтальный список/переключение
  колонок без потери действий.
- Всегда обрабатывайте `loading`, `error`, `empty` и `success`; ошибка загрузки
  не маскируется пустой доской. Для повторной загрузки предоставляйте действие.
- Используйте нативную семантику: `button` для действий, `label` для полей,
  видимый фокус, понятные текстовые ошибки и управление с клавиатуры.
- Для приоритета не полагайтесь лишь на цвет: выводите текстовую метку.

## Качество и проверки

- Перед передачей изменений запускайте относящиеся к ним форматирование,
  lint, typecheck, unit/integration-тесты и production build, если это возможно.
- Минимум покрываются тестами: валидация входных данных, бизнес-логика
  перемещения/обновления задачи, а также ключевой API-сценарий. Тесты должны
  быть независимы от внешних данных.
- В README фиксируйте точные шаги запуска БД, API и frontend, переменные
  окружения, команды миграций и проверок, известные ограничения, принятое
  небольшое UX-улучшение, затраченное время и то, где AI помогал. Любой код,
  предложенный AI, проверяется typecheck, тестами, линтером и ручной проверкой
  ключевого сценария в браузере.

## Git-процесс

- Агент не выполняет `git add` и `git commit`. После готового изменения он
  предлагает название и состав атомарного коммита; коммит создаёт пользователь.
- История состоит из маленьких, логически завершённых и собираемых коммитов.
  Один коммит меняет одну связанную часть поведения, без смешивания рефакторинга
  и новой функциональности.
- Сообщения коммитов пишите в повелительном наклонении и отражайте результат:
  `feat(tasks): add validated list filters`.
- Перед коммитом проверяйте diff на случайные файлы, единообразие форматирования
  и релевантные проверки проекта.
- Не переписывайте чужие изменения и не объединяйте несвязанные правки ради
  удобства ветки.
