# Вехи разработки задачника

## 1. Каркас проекта и локальная среда

**Вход:** пустой репозиторий и согласованное ТЗ.

**Работы:** создать workspace с `apps/web` и `apps/api`; настроить TypeScript,
линтер, форматтер, тестовый раннер и общие команды. Добавить Docker Compose для
PostgreSQL, `.env.example` для приложений и базовый README с локальным запуском.

**Выход:** с чистого клона можно поднять PostgreSQL одной командой, запустить API
и web-приложение отдельно, а `lint`, `typecheck`, `test` и `build` имеют
документированные точки запуска.

**Проверяемый результат:** `docker compose up -d db`, затем команды запуска API
и web открывают их локальные адреса без ручной настройки, кроме копирования
`.env.example` в `.env`.

## 2. Модель данных и API задач

**Вход:** рабочее окружение и доступная PostgreSQL.

**Работы:** описать Prisma-модель задачи и миграцию; реализовать NestJS-модуль
задач с runtime-валидацией DTO, единым форматом ошибок и CRUD API. Статусы:
`NEW`, `IN_PROGRESS`, `DONE`; приоритеты — закрытый набор значений. Добавить
Swagger и тесты валидации, сервисной логики и одного API-сценария.

**Выход:** API является единственным источником данных для задач и переживает
перезапуск сервера благодаря PostgreSQL.

**Проверяемый результат:** после применения миграции запросами API можно создать
задачу с названием, описанием и приоритетом, получить список/одну задачу,
отредактировать, сменить статус и удалить её. Невалидные запросы возвращают
понятную 4xx-ошибку; тесты проходят.

## 3. Клиент данных и модель доски

**Вход:** доступный, задокументированный API задач.

**Работы:** определить контракты и Zod-схемы на frontend-границе, создать
типизированный API-клиент и hooks для списка, создания, редактирования,
удаления и смены статуса. Реализовать чистые функции группировки задач по
колонкам и их тесты. Настроить единый слой обработки API-ошибок.

**Выход:** UI может получать и изменять данные только через проверенный клиент;
правила группировки не живут в компонентах.

**Проверяемый результат:** при обновлении страницы клиент снова получает
созданные ранее данные из БД; frontend-сценарии проверяются вручную в браузере.

## 4. Интерфейс доски и управление задачами

**Вход:** готовый клиент данных и API.

**Работы:** собрать MUI-интерфейс из доски, трёх колонок, карточки задачи,
диалогов создания/просмотра/редактирования и подтверждения удаления. Реализовать
перемещение между колонками доступными кнопками смены статуса; drag-and-drop не
обязателен. Отобразить приоритет текстом и доступной визуальной меткой.

**Выход:** пользователь выполняет все сценарии ТЗ через браузер.

**Проверяемый результат:** в каждом из трёх статусов отображается своя колонка;
можно создать, просмотреть, изменить и удалить задачу, а также перенести её в
другую колонку. После перезагрузки состояние сохраняется, поскольку повторно
читается из PostgreSQL.

## 5. Адаптивность, состояния и финальная приёмка

**Вход:** функциональная доска.

**Работы:** адаптировать layout для desktop и телефона; явно оформить состояния
загрузки, ошибки с повтором, пустой доски и успеха. Провести ручную проверку в
узком и широком viewport, запустить полный набор проверок, дополнить README
решениями, ограничениями, временем и использованием AI.

**Выход:** приложение готово к локальной демонстрации и передаче.

**Проверяемый результат:** на desktop видны три удобные колонки; на телефоне
все колонки и действия доступны без обрезанных элементов. При недоступном API
видны ошибка и кнопка повтора, при отсутствии задач — понятное empty-состояние.
`lint`, `typecheck`, `test` и production build проходят.

## Предлагаемое небольшое улучшение

Добавить быстрый фильтр по приоритету в шапке доски. Он поможет выделить срочные
задачи в заполненной доске и не меняет обязательную модель задач. Реализацию
можно оставить за рамками первой версии; если она войдёт в объём работ, фильтр
должен быть доступен с клавиатуры и иметь действие сброса.
